# Bellcast — Architecture

Status: design draft, pre-build
Last updated: 2026-10-25

## 1. Decisions

| Area | Decision |
|---|---|
| Product model | Single-tenant, self-hosted instance. One owner, one API key, one Supabase project, one Vercel deployment. No accounts. |
| Hosting | Next.js on Vercel, Postgres on Supabase. |
| ntfy compatibility | **Not a goal.** Own API, own semantics. |
| Web app | Next.js App Router. The product UI lives at `/app`. |
| Desktop | Tauri v2 wrapper for Windows, macOS, Linux that loads the deployed web UI. No duplicated UI. |
| Landing/docs | Stays in the separate `bellcast-landing` repo. Not merged. |
| Realtime transport | Authenticated long-polling through the Next API (recommended). No Supabase client in the browser. |
| Background delivery | Desktop app runs in the tray/at login. Web notifications only while a tab is open. |
| v1 non-goals | Accounts, mobile apps, attachments, ntfy protocol, self-contained binary, web push, multi-instance. |

### Why single-tenant changes the design

Because there is exactly one human and one trust boundary, **topics are organization, not
security boundaries**. Anyone with the instance key can read every topic. That removes the
need for per-user grants, RLS read policies, and a client-side Supabase session.

This is the single biggest simplification in the project. Protect it.

## 2. System overview

```
                 ┌──────────────────────────────┐
  curl / CI ────▶│  Next.js on Vercel           │
                 │  /api/v1/publish/{topic}     │──┐
                 │  /api/v1/sync (long-poll)    │  │ service_role
                 │  /api/v1/session             │  ▼
  Browser ──────▶│  /app (React)                │┌─────────────┐
                 └──────────────────────────────┘│  Supabase   │
                                                 │  Postgres   │
  Tauri ────────▶ loads https://instance/app     └─────────────┘
```

- **Vercel** is both the UI host and the only API surface.
- **Supabase** is only a database. No Realtime, no anon key, no client SDK.
- The service role key never leaves the server.
- All reads and writes go through one authenticated API, which makes the security model
  small enough to reason about.

### Why not direct Supabase Realtime

Direct Realtime would require either minting custom Supabase JWTs or creating a dedicated
Supabase Auth user, plus token refresh and RLS read policies. On current Supabase projects
this means dealing with asymmetric JWT signing keys / imported keys, and getting it wrong
exposes every message to anyone holding the public anon key.

Single-tenant traffic is tiny. A server-mediated long-poll gives sub-second delivery with one
auth mechanism, no anon key in the bundle, and deny-all RLS. If true WebSocket latency is ever
required, add a token-exchange endpoint and opt into Realtime as a second transport without
changing the data model or the UI.

## 3. Authentication

Two credentials, one secret:

- **API key** — generated by the operator (`openssl rand -hex 32`), stored in
  `BELLCAST_API_KEY` on Vercel. Used by CLI/CI via `X-API-Key` or `Authorization: Bearer`.
- **Session cookie** — the browser/desktop exchanges the API key once for an HttpOnly
  cookie. The key is never stored in `localStorage`.

Flow:

```
POST /api/v1/session   { "key": "..." }
  → compare (SHA-256 + timingSafeEqual)
  → Set-Cookie: bellcast_session=<key>;
      HttpOnly; Secure (in production); SameSite=Lax; Path=/; Max-Age=31536000
```

- All `/app` and `/api/v1` reads use the cookie.
- CLI publishing uses the header.
- `Origin` is checked on cookie-authenticated state-changing requests (CSRF).
- Rotating the env key invalidates every existing session immediately.
- No users table, no passwords, no OAuth.

The desktop app opens `/connect#key=<key>` so the web UI can exchange the key for the
cookie without the user pasting it twice. The fragment stays in the webview. The Rust
poller keeps its own copy of the key for background delivery (see §8).

## 4. Data model

```sql
create extension if not exists pgcrypto;

create table public.topics (
  id              uuid primary key default gen_random_uuid(),
  slug            text not null unique
                    check (slug ~ '^[a-z0-9][a-z0-9_-]{0,63}$'),
  created_at      timestamptz not null default now(),
  last_message_at timestamptz
);

create table public.messages (
  seq             bigint generated always as identity primary key,
  id              uuid not null unique default gen_random_uuid(),
  topic_id        uuid not null references public.topics(id) on delete cascade,
  title           text,
  body            text not null,
  priority        smallint not null default 3 check (priority between 1 and 5),
  tags            text[] not null default '{}',
  click_url       text,
  actions         jsonb,
  idempotency_key text not null default gen_random_uuid()::text,
  created_at      timestamptz not null default now(),
  unique (topic_id, idempotency_key)
);

create index messages_topic_seq_idx on public.messages (topic_id, seq desc);
create index messages_seq_idx         on public.messages (seq);
create index messages_created_idx     on public.messages (created_at);

alter table public.topics   enable row level security;
alter table public.messages enable row level security;

-- No policies. Clients never talk to Postgres directly.
revoke all on public.topics   from anon, authenticated;
revoke all on public.messages from anon, authenticated;
```

Notes:

- `seq` is the sync cursor. Never use `created_at` as a cursor.
- Priority is stored as `1..5` (`min, low, default, high, max` at the edge).
- `actions` is validated JSON, never rendered as HTML.
- Unread/read state is **local per device** in v1. No server table.
- No Realtime publication, no `messages` row streaming.

### Publish RPC

A single Postgres function keeps topic creation, idempotency, and `last_message_at`
consistent:

```sql
create or replace function public.publish_message(
  p_slug    text,
  p_title   text,
  p_body    text,
  p_priority smallint,
  p_tags    text[],
  p_click   text,
  p_actions jsonb,
  p_idem    text
) returns public.messages
language plpgsql
security definer
set search_path = public
as $$
declare
  v_topic uuid;
  v_msg   public.messages;
begin
  insert into topics (slug) values (p_slug)
    on conflict (slug) do update set slug = excluded.slug
    returning id into v_topic;

  insert into messages
    (topic_id, title, body, priority, tags, click_url, actions, idempotency_key)
  values
    (v_topic, p_title, p_body, p_priority, coalesce(p_tags, '{}'),
     p_click, p_actions, p_idem)
  on conflict (topic_id, idempotency_key) do nothing
  returning * into v_msg;

  if v_msg.id is null then
    select * into v_msg from messages
      where topic_id = v_topic and idempotency_key = p_idem;
  end if;

  update topics set last_message_at = v_msg.created_at where id = v_topic;
  return v_msg;
end;
$$;
```

### Retention

`BELLCAST_RETENTION_DAYS` (default 30). Use Supabase `pg_cron` when available:

```sql
select cron.schedule(
  'bellcast-prune',
  '0 3 * * *',
  $$delete from public.messages
    where created_at < now() - interval '30 days'$$
);
```

Fallback: a Vercel cron hitting `GET /api/cron/prune`.

## 5. API

Base: `/api/v1`. All responses JSON. Errors: `{ "error": { "code": "...", "message": "..." } }`.

### Session

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `POST` | `/session` | key in body | Set HttpOnly cookie |
| `DELETE` | `/session` | cookie | Sign out |
| `GET` | `/session` | cookie | `{ authenticated: true }` |

### Health

`GET /health` → `{ ok: true, version, time }`. No secrets, no auth.

### Publish

`POST /publish/{topic}`

```bash
curl -X POST https://your-instance.vercel.app/api/v1/publish/backups \
  -H "X-API-Key: $BELLCAST_API_KEY" \
  -H "Title: Backup OK" \
  -H "Priority: high" \
  -H "Tags: backup,success" \
  -H "Click: https://dashboard.example.com" \
  -H "Idempotency-Key: backup-2026-10-25" \
  -d "Backup completed successfully"
```

JSON body is also accepted (`Content-Type: application/json`):

```json
{
  "title": "Backup OK",
  "body": "Backup completed successfully",
  "priority": "high",
  "tags": ["backup", "success"],
  "click": "https://dashboard.example.com",
  "actions": [{ "action": "view", "label": "Open", "url": "https://..." }]
}
```

Rules:

- Topic slug `[a-z0-9][a-z0-9_-]{0,63}`, auto-created.
- Body ≤ `BELLCAST_MAX_BODY_BYTES` (default 64 KiB).
- Priority: `min|low|default|high|max` or `1..5`.
- Tags: up to 10, comma-separated or array.
- URLs: `http`/`https` only.
- Idempotency: same key + topic returns the original message.
- Response `201`: `{ "message": { id, seq, topic, created_at, ... } }`.
- Optional CORS for `/publish/*` (`Access-Control-Allow-Origin: *`, no credentials).
- Optional rate limit via Upstash; no-op when unset.

### Read

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/topics` | Topics with `last_message_at`, last message preview |
| `GET` | `/messages?limit=100&before=<seq>&topic=<slug>` | Paged history, newest first |
| `GET` | `/sync?since=<seq>&wait=25&topic=<slug>` | Long-poll for new messages |
| `DELETE` | `/messages/{id}` | Delete one message |

`/sync` holds the request up to `wait` seconds (max 25). The server checks for rows every
500 ms and returns as soon as it finds any, so normal latency is under a second. On timeout it
returns an empty list. The client immediately reissues the request.

```json
{
  "messages": [ ... ],
  "cursor": 1421,
  "reset": false
}
```

`reset: true` means `since` is older than retention; the client clears its cache and
bootstraps again.

### Message shape

```json
{
  "id": "uuid",
  "seq": 1421,
  "topic": "backups",
  "title": "Backup OK",
  "body": "Backup completed successfully",
  "priority": 4,
  "tags": ["backup", "success"],
  "click": "https://dashboard.example.com",
  "actions": [],
  "created_at": "2026-10-25T12:00:00Z"
}
```

## 6. Sync and offline cache

- IndexedDB via Dexie, database `bellcast`, scoped to the instance origin.
- Tables: `messages` (`seq` PK, indexes on `topic`, `[topic+seq]`, `created_at`),
  `topics`, `meta` (`cursor`, `lastRead:<topic>`).
- Boot:
  1. Hydrate from Dexie (instant UI).
  2. `GET /topics`.
  3. `GET /messages?limit=100` for the newest page, merge, set `cursor = max(seq)`.
  4. Start the `/sync` loop from `cursor`.
- Reconnect after sleep/network loss: same loop; the server fills every gap from `cursor`.
- Deduplicate by `seq` (and `id`).
- Older history: `before=<oldest seq>` on scroll.
- On `401`: stop the loop and route to `/connect`.
- Backoff on network errors: 1s → 30s with jitter.
- `AbortController` on unmount; a new tab simply runs its own loop (no leader election in v1).
- Read state and unread counts are local. No cross-device read sync in v1.

Tradeoff accepted: ~0.5–1.5 s delivery instead of ~100 ms. This is invisible for
notifications and removes the entire client-side Supabase auth problem.

## 7. Web app

Next.js App Router, Tailwind/shadcn, dark by default, design tokens aligned with the landing
page.

| Route | Purpose |
|---|---|
| `/` | Redirect to `/app` or `/connect` |
| `/connect` | Paste API key, verify, set cookie |
| `/app` | Main shell |
| `/app/t/[topic]` | Topic view |
| `/app/settings` | Notifications, cache, sign out, health, curl snippet |

Layout: topic sidebar + message list + optional detail pane. Responsive down to a single
pane. Message body is rendered as **plain text** in v1 (no markdown, no
`dangerouslySetInnerHTML`).

Actions:

- **New** — compose/test notification (topic, title, body, priority, tags, click).
- **Copy curl** — generates a working publish command for the current topic.
- **Notification permission** — browser notification while the tab is open.
- **Clear cache**, **Sign out**.

Server rendering is limited to the shell and API. Message data is client-side only; this is
also what makes the desktop wrapper trivial.

State: Dexie as source of truth + `useLiveQuery`; a small Zustand store for UI state; no
TanStack Query needed.

## 8. Desktop app (Tauri v2)

The desktop app is a Rust shell around the deployed web UI. It does not bundle a second
frontend.

### Lifecycle

1. First launch: a bundled onboarding page collects the instance URL and API key.
   Rust validates them with `GET /api/v1/health` before writing anything.
2. Store both in `config.json` under the app config directory (owner-only permissions in
   v1; OS keychain is a follow-up). Enable start at login.
3. Open `/connect#key=<key>` in the main window. The web app POSTs the key to
   `/api/v1/session`, gets the HttpOnly cookie and redirects to `/app`. The fragment is
   removed from the address bar immediately and never leaves the webview.
4. Inject a tiny bootstrap global before the page loads:

   ```js
   window.__BELLCAST__ = {
     platform: "desktop",
     instanceUrl,
     openExternal(url) { /* custom-scheme hand-off to Rust */ }
   };
   ```

   `notify` is intentionally absent: native notifications come from Rust, so remote pages
   need no Tauri IPC or runtime capability at all.
5. Start the background poller. It long-polls `/api/v1/sync` with `X-API-Key`, persists the
   cursor, and raises a native notification for each message. It skips notifications while
   the main window is focused, because the feed is already visible.

### Native behavior

- Tray icon: Open, Pause notifications, Start at login, Settings, Quit.
- Autostart at login; single-instance (focus existing window).
- Native notifications through a small `bellcast_notify` command so title, body, priority,
  click target, and dedupe are controlled. Click focuses the window.
- External links open in the system browser, validated `http(s)`.
- Navigation guard: only the configured instance origin (plus the local holding/onboarding
  pages) may load in the main webview. Everything else opens externally. This prevents
  redirect-to-attacker + IPC exposure.
- No `fs`, `shell`, or arbitrary HTTP plugin permissions.
- Optional badge count.

### Updates and distribution

- `tauri-plugin-updater` with a signed manifest hosted on GitHub Releases.
- Signing keys in CI secrets from the first release.
- macOS: Developer ID + notarization (Apple Developer account required).
- Windows: code signing recommended (otherwise SmartScreen warnings).
- Linux: AppImage + `.deb`.
- CI matrix: `tauri-apps/tauri-action` on tag, three OSes, draft release.

### Known limitation

Cold start requires network to load the remote UI; after the first load the SPA and IndexedDB
cache keep working offline. Bundling a static build of the same UI later removes this, at the
cost of a second build target.

## 11. Self-hosting flow

1. Create a Supabase project.
2. Apply `supabase/migrations` (Supabase CLI or SQL editor).
3. `openssl rand -hex 32` → `BELLCAST_API_KEY`.
4. Import the repo into Vercel, set the root directory to `apps/web`, add env vars.
5. Deploy. Open `https://your-app.vercel.app/connect`, paste the key.
6. Publish the first notification:

   ```bash
   curl -d "Hello" -H "X-API-Key: $BELLCAST_API_KEY" \
     https://your-app.vercel.app/api/v1/publish/test
   ```

7. Desktop: install, enter instance URL + key, enable start at login.

Optional: a Vercel “Deploy” button and the Supabase integration for env provisioning.

## 12. Security checklist

- RLS enabled, deny-all; only `service_role` touches tables.
- No anon key or Supabase client in the browser.
- API key compared with SHA-256 + `timingSafeEqual`.
- Cookie `HttpOnly; Secure; SameSite=Lax`; `Origin` checked on mutations.
- Publish body and topic limits; URL scheme validation; no HTML rendering.
- Rate limiting (optional Upstash) and per-IP/key thresholds.
- No secrets in logs; redact `Authorization`, `X-API-Key`, cookies.
- CSP and standard headers in Next config.
- Desktop: runtime capability scoped to one origin, navigation allowlist, keychain storage,
  no filesystem/shell permissions, signed updater.
- Supabase service role key is the crown jewel; document that clearly.
- Backups: Supabase daily backups on paid plans; document manual `pg_dump`.

## 13. Limits and tradeoffs

| Limit | Impact | Mitigation |
|---|---|---|
| ~0.5–1.5 s delivery | Not literally instant | Acceptable for notifications; Realtime is an optional upgrade |
| Vercel function duration | Long-poll capped at 25 s | Reissue immediately; reconnects are cheap |
| Vercel Hobby is non-commercial | Cannot host a paid service | Pro for hosted; Hobby fine for self-host |
| Supabase free project pauses after 7 days idle | Notifications stop | Document Pro; polling usually keeps it active |
| Web notifications need an open tab | No closed-tab delivery | Desktop app in tray is the background client |
| Remote UI cold start needs network | Blank app if offline at launch | Holding page; bundled UI later |
| No attachments | Bigger payloads impossible | v2 with Supabase Storage |
| Single instance, single key | All topics share one trust boundary | Fine by definition; per-topic keys later |
| Read state is per device | No cross-device unread sync | Local only in v1 |
